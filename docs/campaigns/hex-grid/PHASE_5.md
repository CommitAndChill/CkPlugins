### P5a • Construction provenance

The independent architecture review found no existing pre-composition classification. The loader maps runtime rows before the construction pump (`CkSnapshot_Subsystem.cpp:1244-1255,1427-1437`), adopts already created nested children by their saved owner, label and creation order (`:1042-1061`), and resolves engine-owned keys independently (`:1028-1039`). **Recommended framework change for the Technical Director.** Preserve existing reconstruction routes. Add a CkEcs-owned internal contract for initialization disposition per entity, projected payload type and load epoch. CkSnapshot owns a manifest from the saved rows, classifies the specific construction/adoption candidate and reports terminal delivery. CkGrid consumes this neutral declaration at or before publishing its typed board. It neither reads snapshot tags nor depends on CkSnapshot. This is a separately approved Tier 4 slice, preceding P5b's hex handler. It changes shared persistence infrastructure. The approved topology choice alone is insufficient authority for that expansion.

| Neutral disposition | Who may establish it and what the board does |

| Baseline expected | Exact saved row, load epoch and projected type are bound. Await atomic commit of that baseline and coherent release. |
| Terminal | Loader reports missing, rejected, timed out, cancelled or released. Only a matching committed epoch may open Ready. Prior-epoch delivery is ignored. Forced release can close a failed board as Unavailable. |

CellRules is a sparse, canonical array of coordinates whose current local tags or manual blocked vote differ from their recipe defaults. A present entry is a full replacement of those two local fields, so an explicitly cleared authored tag is representable. Reject duplicate/out-of-domain rule rows and duplicate blocker names. Identical key/handle replay succeeds without new notifications. A different key for the same handle, or a duplicate key on a different live handle, rejects without displacing the incumbent.

**Occupant association across load.** Keep a feature-scoped authority-issued nonzero binding GUID on each independently resolvable hex object. A board stores this key alongside the optional remapped handle. Multiple instances of the same object recipe have distinct keys. Persist the key on the object itself with a separate small typed identity payload; its own save handler is independent of the single board-state registrar. Register an object's accepted key against its actual local handle and notify matching pending reservations inside that gameplay world's hex feature. Support either arrival order. Use world-lifetime-scoped weak/versioned handles and keyed waiters, unsubscribe on move, replace, destroy, teardown or world travel; never scan globally or create an engine-wide identity service. Duplicate live keys cannot bind or overwrite another object. On an unresolved reference, reserve by placement ID immediately; preserve the key through subsequent save cycles. Compare only accepted keys. During restore, defer association until the object's identity payload is accepted even when a remapped handle is already live. If a handle is provided, require it to equal the accepted key's registered handle. A nonzero binding key may be claimed by only one active hex placement across committed boards in the same gameplay world, even when the occupant is unresolved. Publish or release that claim atomically with the owning placement. A conflicting known key rejects the entire incoming projection, preserving both boards. A newly discovered conflict in the eventual actual object association preserves the pending reservation under its placement ID. A key/flag mismatch (anonymous with nonzero key or referenced with zero key) is malformed. Exercise both arrival orders, fresh object during load, duplicate unresolved keys across boards and same-object replay/change. Non-reconstructible occupants can remain reserved and unresolved. If the required object has no production identity/transport lifecycle, keep its reservation and surface the limitation before promising association. This policy uses two payload types (board state and object identity), each registered once. It adds no public generic identity service.

Use P4 canonical view/rule structures rather than duplicate their definitions; durable entries must contain every mutable rule override that affects admission. Persist exact contributor identities/active states and recompute counts; never save aggregate counts alone or live blocker/cell/placement entity handles. Placement IDs and blocker IDs are nonzero FGuid, durable and scoped by board; distinct anonymous placements have distinct IDs. Every *valid* occupant may have at most one placement across all hex boards in the same world, enforced by P4 hex-specific backref.

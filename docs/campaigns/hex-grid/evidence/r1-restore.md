# R1 authority restore attribution

The first cap-3 diagnostics at 50% and 90% occupancy were profiled on the i9-10900KF workstation using the identical staged Win64 dedicated server, process-local Iris cap 3, no connected client during authority load, and two radius-32 boards. These are two diagnostic examples, one per density. The cohort wall-clock evidence below covers the repeated runs separately.

## Capture controls and repeated observations

Each materialized authority had a fresh process and save slot. Client and authority manifest hashes matched within all 24 retained pairs, and all payload and entity census checks closed. Both boards were restored before the client connected. The cap groups therefore provide independent restore samples rather than a treatment that should affect restore. ## Board versus object hydration

The saved table contains two board payloads first and one durable identity per object thereafter. The synchronous enqueue loop visits that order. Each owner has one payload, a fresh holder and exactly one traced holder construction. The per-entity apply dispatcher visited 3,170 / 5,706 rows. The final two dispatch rows each created exactly 1,584 / 2,852 placement child entities under the board projection path. The identities applied first in both traces despite the saved table containing board rows first. The identity handler registers the stable binding and creates no placement entities. All child creations, raw payload counts and per-row scopes reconcile. The elapsed time for each apply row includes eligibility checks, the typed callback and completion accounting for that entity. It cannot separate board decode, transaction preflight and commit within the callback. ## Bounds on load entry and manifest verification

The fixture times Request_Load through the return of successful Verify. It subsequently hashes the manifest, writes the authority restore CSV, runs a separate offline inspector, writes readiness and advances to phase 5. Those later operations explain why timing all of frame 370 or 210 as verification would overstate fixture cost. The last save timing message precedes LoadStart and the first provenance message follows it. Shifting both endpoints by the monotonic restore duration gives a bracket for Verify completion. An optional tighter upper bound uses the original CSV's NTFS last-write time on this same PC. The role-log bounds have a one-millisecond outward allowance at each endpoint. Keep the log-only bounds if the artifact was copied or wall-clock continuity is uncertain. [Fixture timing and gate order](../../../../Plugins/CkTests/Source/CkTests/Private/HexGrid/CkHexDenseAcceptance.cpp#L428) · [Per-run bounds and original times](r1-restore-wall.csv)

**The selected authorities each executed Verify once after restore, and that call succeeded.** The fixture skips Verify while the load remains in progress. After READY, the complete upper QPC envelope around possible verification contained exactly two starts of ForEachObjectOfClasses_Implementation in one core-ticker invocation at each density. Every call begins with one class query for mixed pieces. Success additionally requires one for boards. The matching success consumes both observed entries. An unsuccessful call would have added at least one. The first-to-second query took 0.92 / 1.63 ms. The clock and enclosing ticker bound the full successful Verify duration to **23.14–33.65 / 39.73–66.43 ms**. Using the original NTFS receipt upper bound tightens the upper endpoints to **27.21 / 44.98 ms**. These results apply to the two decoded authority traces. Other rows have role logs and receipts but no independently decoded query counts. The exact allocation, lookup, formatting and sorting split remains unresolved. [Raw count and time bounds](r1-restore-verify.csv) · [Actor iteration in Verify](../../../../Plugins/CkTests/Source/CkTests/Private/HexGrid/CkHexDenseAcceptance.cpp#L204)

The end-to-end stopwatches on these two cases were **1,153.04 / 2,056.36 ms**. Even subtracting the full measured rebuild interval and the upper log-only bound on the successful Verify leaves at least **534.6 / 806.1 ms** in these observations. These two exclusive intervals cannot alone close the 250 ms release budget. The measured stages justify independent restore work on reconstruction and payload admission/application while preserving the load and verification endpoints.

## What can select an optimization

1. **Entity reconstruction.** The 50/90% dominant rebuild frames are 580.6/1,176.6 ms. The cost extends beyond raw actor spawning. Profile spawn-handler bridge/link, retained recipe allocation, script construction and signal/driver setup individually before changing lifetime or pooling behavior. Existing trace scopes distinguish the CreateObject child from the rest of the request. [Spawn handler](../../../../Plugins/CkFoundation/Source/CkEcs/Public/CkEcs/EntityScript/CkEntityScript_Processor.cpp#L149)
2. **Hydration.** The two board rows cost more to apply than every identity combined at both densities. Target board projection validation, staging, placement-child creation and commit for the next attribution pass. If changing serialization is under consideration, separate the first-board deserialize from the orphan census and per-row queue insertion. The measured type split prioritizes the next experiment without establishing a codec change or permitting an altered saved representation. [Snapshot enqueue](../../../../Plugins/CkFoundation/Source/CkSnapshot/Public/CkSnapshot/Subsystem/CkSnapshot_Subsystem.cpp#L1771) · [Typed hydration callbacks](../../../../Plugins/CkFoundation/Source/CkGrid/Public/CkGrid/HexGridSystem/Persistence/CkHexGridPersistence_Fragment.cpp#L53)
3. **Publication and convergence.** Measure the post-lift ticker callbacks and board versus object publication separately. The named idle contribution is bounded and too small to recover the full deficit. Preserve whole-set quarantine, setup ordering and consecutive settled-frame semantics. [Quarantine and convergence](../../../../Plugins/CkFoundation/Source/CkSnapshot/Public/CkSnapshot/Subsystem/CkSnapshot_Subsystem.cpp#L3559)
4. **Fixture cost.** Add diagnostic-only entry, exit, rejection reason and row count to Verify if choosing to optimize its contribution. Keep the public success criteria and the original clock. An earlier milestone can be reported alongside the existing clock if it is explicitly labeled.

## Reproduction and validity

Read the completed authority receipts and each server and client manifest using r1-restore-wall.py. The script checks effective command-line capture mode, cap readback, manifest hashes, mapped row counts, payload accounting, convergence and both process exits. Each case uses its own stable identities. The supervisor's pairing or shaping failures remain visible in the exclusion ledger. Wall clock replay (source workstation, `r1-restore-wall.py`) · [Excluded observations](r1-restore-excluded.csv)

Run r1-restore-cpu.py after creating the shared marker CSV and the four native frame exports below. It partitions the GameThread's protocol-7 CpuProfiler.EventBatchV3 stream at each measured LoggingLogMessage QPC, assigning every tick to the deepest active batch scope. The intervals from earliest to latest verification, and from save timing to provenance, involve bounded occupancy of the release clock. Other event loggers, workers and OS stacks cannot be distinguished by this batch-only measure. The native analyzer includes additional scoped events, so exact equivalence is checked only for comparable scopes and intervals. Both original server log frame IDs are below 1,000 and map directly to trace frame indices.
